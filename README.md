## 1. プロジェクト概要と開発背景

私は高専ロボットコンテストでの優勝を目指すチームのリーダーを務めている。メンバーのタスク管理や戦略の洗練を行う中で、開発スピードを著しく低下させる深刻な問題に直面していた。それは「資材の在庫管理の属人化と、欠品による開発の遅延」である。

ロボット製作において、ネジ一本や特定の電子部品が手元にないことは、その日の作業の完全な停止を意味する。しかし、これまでのチームの運用では以下のような課題が頻発していた。

* 誰が見ても「今なにが何個あるか」がわからない状態になっている
* 在庫が最低限必要な数を下回ってから気づくため、部品の調達が後手に回る
* 保管場所、単価、購入先URLなどの情報が散在しており、補充判断に時間がかかる
* 管理情報が特定の担当者に依存し、そのメンバーが不在だと運用が止まる

「あれがない、これがない」と騒ぎになってから発注する泥縄式の運用を脱却し、在庫情報を可視化して補充判断から発注までのリードタイムを最小化することが急務であった。

大会に向けた開発の手を止めないため、2026年2月18日から2月22日までの5日間、計15時間という短期間で集中的に本アプリケーションの設計と実装を行った。

## 2. 提供機能と解決した課題

* **在庫と補充基準値の一元管理:** 在庫数と補充の目安となる基準値を一つの画面で確認可能とした。
* **補充対象の自動ハイライト:** 基準値を下回ったアイテムを視覚的に強調し、補充が必要な物品を即時に把握できる。
* **情報の統合表示:** 保管場所、単価、購入先リンクをアイテムカード内に統合し、確認から発注までの作業導線を短縮した。
* **直感的な管理機能:** 管理画面から在庫アイテムやカテゴリの追加および編集を容易に行えるようにした。

## 3. 技術的な工夫と設計思想

フロントエンドの実装からインフラ環境の制約を考慮した設計まで、実際のチーム運用を想定した開発を行った。

### フロントエンド実装とUI設計

* Next.jsのApp Routerを採用し、画面ごとの役割を明確に分割した。
* 在庫カード、統計情報表示、ページ内遷移などのUIコンポーネントを設計した。
* ReactのフックであるuseMemoとuseEffectを活用し、ブラウザのローカルストレージとコンポーネントの表示状態を同期させた。

### バックエンドおよびデータ設計の基礎

* API Routeを用いてデータの作成、読み取り、更新、削除の処理を実装した。
* データへのアクセス処理を特定のファイルに集約し、保守性を向上させた。
* 不正なデータの入力や必須項目の欠落を防ぐ検証機能と、エラーハンドリングを実装した。

### 運用環境の制約を考慮した設計

* デプロイ先であるVercelが持つ「読み取り専用ファイルシステム」という制約をあらかじめ把握し、対策を行った。
* 制約に対する現実的な解決策として、まずは「閲覧専用」としての運用を提供し、将来的な外部データベースへの移行を選択肢として設計に組み込んでいる。

## 4. 技術スタック

* **フレームワーク:** Next.js 15 App Router
* **開発言語:** TypeScript

## 5. アプリケーション構成

### データ処理の流れ

1. 初期アクセス時、トップページが所定のJSONファイルを初期データとして読み込む。
2. ユーザーの端末側で、ダッシュボード画面がローカルストレージのデータを優先的に読み込み表示する。
3. ユーザーが行った編集操作はローカルストレージに保存され、再訪問時にその状態を復元する。
4. アイテムやカテゴリの追加・編集はAPIを経由してデータ保存用のロジックを呼び出し、ローカル環境のJSONファイルを更新する。

## 6. ローカル開発環境の構築手順

リポジトリをダウンロードした後、以下のコマンドで開発環境を立ち上げることができる。

```bash
# パッケージのインストール
npm install

# 開発用サーバーの起動
npm run dev

```

ブラウザで http://localhost:3000 にアクセスして動作を確認する。

その他コマンド:

* `npm run build`: 本番用アプリケーションの生成
* `npm start`: 生成済みアプリケーションの起動
* `npm run lint`: ソースコードの静的解析の実行

## 7. デプロイと運用上の注意事項

本アプリケーションはVercelへのデプロイに対応しているが、以下の運用上の制約が存在する。

* **Vercelのファイルシステム制約:** Vercelの実行環境は一時的であるため、APIを通じたJSONファイルへの書き込み処理は永続化されない。管理画面からの追加や更新は、サーバー再起動時にリセットされる。
* **推奨される運用方針:** 本番環境であるVercelでは「閲覧およびフロントエンドでの状態変更」に限定した運用を推奨する。根本的なデータの更新は、ソースコード管理ツール上のJSONファイルを直接編集し、再度デプロイを行う手順を想定している。

## 8. 今後の拡張展望

チームでの実運用をさらに強固なものにするため、以下の機能追加を構想している。

* **外部データベースへの移行:** データ保存先をVercel KVやSupabaseなどのクラウドデータベースへ切り替え、本番環境でもブラウザから完全にデータを操作できるようにする。
* **認証機能の導入:** 管理画面へのアクセスに制限を設け、安全な運用体制を構築する。
* **操作履歴の記録:** 誰が、いつ、どの在庫を更新したかを記録し、確認できる機能を追加する。
* **品質保証の自動化:** GitHub Actions等を用いた自動化環境の構築および、各種テストを導入する。
